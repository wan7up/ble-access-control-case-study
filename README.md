# iPhone 小区门禁抓包与 BLE 交互分析记录

这是一个匿名化的技术案例记录，整理一次“移动 App + HTTP + BLE 门禁”分析项目的过程、结论和经验，供类似场景参考。

> 本仓库不包含真实小区名称、服务器地址、账号会话、门禁 MAC、APK、抓包文件、SSH 凭据、挑战响应密钥或可直接开门的代码。

记录日期：2026-10-01。以下是一个具体系统的测试观察，不代表其他门禁产品的通用协议。

## 结论摘要

- 仅复制 App 的 HTTP 请求不能完成开门。
- 实验中观察到了服务端会话、账号钥匙校验和点击开门时的 HTTP 请求；仅凭抓包无法断言供应商内部如何使用这些请求。
- 实际门禁交互还需要手机在现场通过 BLE 连接对应设备，并完成 GATT 通知、挑战和响应写入。
- 本次在 iPhone 上通过支持所需 Web Bluetooth API 的第三方浏览器验证了 BLE 流程；设备授权和浏览器前台运行仍是必要条件。
- 自动识别可以通过 BLE 广播和 RSSI 做候选排序，但相邻门的信号可能接近，RSSI 不能当作绝对位置证明。
- 最终验证版本采用“扫描附近已授权设备、按信号排序、必要时按顺序尝试”的策略。

## 项目范围

本记录覆盖：

1. mitmproxy 抓取移动 App 的 HTTPS/HTTP 行为。
2. 反编译 APK，定位账号授权、设备映射和 BLE 服务调用。
3. 对比“服务端请求”和“现场 BLE 握手”的职责。
4. 在 iPhone 上验证 Web Bluetooth 的设备选择、GATT 连接和通知流程。
5. 记录自动识别、信号强度和流程耗时方面的取舍。

本记录不提供：

- 真实供应商接口地址或请求体。
- 真实用户会话、Cookie、Token 或门禁钥匙列表。
- 真实设备地址或小区拓扑。
- 设备挑战响应算法、密钥或可运行的开门实现。
- 绕过账号授权、设备授权或现场距离限制的方法。

## 关键发现

### HTTP 与 BLE 是两段流程

实验中观察到的抽象流程如下：

```text
手机确认账号授权
        |
        v
服务端接受一次开门尝试
        |
        v
手机扫描并连接现场 BLE 门禁设备
        |
        v
门禁通过通知返回挑战
        |
        v
手机取得授权响应并写回门禁
        |
        v
门禁返回结果
```

因此，服务端返回业务成功并不等于物理门已经打开。手机仍然需要连接正确的现场设备并完成 BLE 交互。

### 账号授权不是永久保证

为了减少等待，实验版本把非空的门禁钥匙列表做了较长时间的缓存，并提供显式“重新授权”操作。公开记录只保留这个设计思想，不保留真实缓存内容或会话材料。

实际部署时应考虑：

- 登录会话可能过期。
- 门禁钥匙可能被撤销或变更。
- 服务端缓存可能短暂滞后。
- 开门请求不能因为网络重试而重复发送。

### 自动识别的限制

BLE 广播可以帮助判断附近有哪些已授权设备，也可以记录 RSSI。但 RSSI 会受墙体、手机方向、人体遮挡和设备发射功率影响。

相邻门的实际策略通常需要：

- 先收集多个样本，而不是只看一个 RSSI。
- 优先平均信号更强的候选。
- 设定“明显领先”的阈值。
- 没有明显领先时，按候选顺序处理。
- 对真实开门请求设置明确的限流和失败边界。
