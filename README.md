# 小区APP蓝牙开门禁复刻方案

这是一份匿名化的实测记录：不使用原小区 App，在 iPhone 上通过网页完成自己账号已授权的门禁开门。记录于 2026-10-01，只说明本次遇到的系统，不代表所有门禁都采用相同协议。

## 开门场景

原 App 展示账号拥有的门禁钥匙。用户到门前点击“开门”，App 会请求服务端，也会通过手机蓝牙与附近的门禁设备通信；离门太远时会提示走近门。我们发现，**服务端返回成功，不等于门已经打开**。只有手机完成现场蓝牙交互，门禁返回成功回执，才有开门的可能，最终仍需现场确认。

## 复刻流程

1. **HTTP 请求。** 点击开门后，程序以已登录账号的授权信息发出一次真实请求，并检查服务端业务结果。账号钥匙列表用于确认有权使用哪些门。单独重放这条请求，服务端可以返回成功，但门禁不会因此自动打开。供应商内部如何使用这条请求，仅凭抓包无法完全确定。
2. **蓝牙部分。** 手机扫描附近的 BLE 广播，从账号允许的门里匹配设备；随后连接对应门禁的 GATT 服务、启用通知，接收门禁发来的挑战，把授权响应写回设备，并等待门禁回执。这里既有接收，也有主动写入，**不是简单的蓝牙配对**。

复刻版本中，网页负责手机上的扫描和蓝牙连接；自建服务保存敏感会话材料、发送 HTTP 请求，并计算门禁挑战所需的响应。手机再把响应写回门禁。它不是“仅靠 HTTP 的网页按钮”，也不是脱离手机蓝牙的远程开门。设备确定后，HTTP 请求和蓝牙连接可以并行启动，但只有 HTTP 业务成功后才继续门禁握手。

## 选用哪种浏览器

- **不需要蓝牙的门禁：** 如果现场验证确认授权的 HTTP 请求本身就能实际开门，可以用普通浏览器做操作页面，必要时由自建服务保管会话并代发请求；不能只凭 HTTP 200 判断这条路线可行。
- **需要蓝牙的门禁：** 像本例这样还要扫描、连接并写入 BLE 设备，就要选择支持所需 Web Bluetooth API 的浏览器。普通浏览器若没有这些接口，单靠网页无法完成蓝牙部分。

## 自动识别与限制

最终使用的版本先扫描附近**已授权**设备，再参考多次广播的 RSSI 排序；信号差距不明显时会按顺序尝试。两扇相邻门可能同时出现，RSSI 也会波动，因此无法保证每次都准确判断最近的门。曾试过跳过扫描、优先直连常用门，实际体验不如扫描版，已撤回。

iPhone 实测使用支持所需 Web Bluetooth API 的 Bluefy。首次使用要授权设备，开门时浏览器须在前台；桌面快捷指令可以唤起浏览器，但不能让网页在后台静默完成 BLE 开门。账号会话也可能过期，需要重新授权。

## 部署方式与网络限制

这类方案可以使用 Cloudflare 托管服务，不必维护自己的服务器：Workers 承担 HTTP 代发、授权检查和挑战响应计算，网页可由 Workers 静态资源或 Pages 托管，敏感配置放在 Secrets 中。迁移时仍需适配运行环境，并验证完整开门流程；手机上的 BLE 扫描、连接和写入不变。

本项目尝试部署到 Cloudflare，已验证账号钥匙接口可用，但用户在中国大陆外出使用时遇到页面无法访问，最终回退到原先可用的自建服务器方案。国内访问 `workers.dev` 等公共入口可能受运营商、地区和网络路径影响；本次未定位具体原因，也不能据此认定所有国内网络都不可用。上线前应在实际使用地点用手机移动网络测试，不能只看电脑端部署成功。

自定义域名并不自动保证国内访问稳定。Cloudflare China Network 是另一项服务，有 Enterprise 和 ICP 备案等接入条件，不能视为普通 Workers 免费入口的直接替代。没有域名、且已有可用服务器时，可以先保留原方案；自建服务器如果仍通过 Cloudflare Tunnel 暴露入口，也仍可能受到入口网络状况影响，需单独验证。

无论采用哪种部署方式，公开仓库都不应放入真实入口、账号会话、密钥、设备地址或可直接执行的开门代码。Cloudflare 只是部署位置的替代方案，不会改变现场 BLE 交互这一前提。

## 公开边界

本项目只针对本人有权使用的账号和门禁。仓库**只发布分析记录**，不发布真实小区、门名、MAC、接口地址、账号会话、APK、抓包原件、挑战响应密钥或可运行的开门代码。
