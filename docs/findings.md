# 实验结论

## 观察到的阶段

| 阶段 | 作用 | 是否足以开门 |
| --- | --- | --- |
| 账号会话检查 | 确认当前账号仍有门禁权限 | 否 |
| 门禁钥匙列表 | 建立账号与设备的映射 | 否 |
| 开门 HTTP 请求 | 创建或授权一次开门尝试 | 否 |
| BLE 设备发现 | 找到现场可见设备 | 否 |
| GATT 连接和服务发现 | 建立与门禁的通信链路 | 否 |
| 挑战与响应 | 完成门禁协议握手 | 接近完成 |
| 门禁回执 | 返回设备侧结果 | 仍应现场确认 |

## 为什么 HTTP 单独不够

在测试中，服务端业务成功响应与门禁实际打开之间还存在 BLE 阶段。离开现场、没有正确设备授权或选择了错误设备时，HTTP 可能成功，但门禁不会完成最终动作。

因此，以下做法都不可靠：

- 只把一次 HTTP 请求做成网页按钮。
- 把 HTTP 200 当作门已经打开。
- 固定使用某一扇门的设备地址。
- 仅凭一次扫描结果认定最近的门。

## 自动模式

自动模式的抽象逻辑：

```text
读取已授权设备
        |
监听附近 BLE 广播
        |
收集设备和 RSSI 样本
        |
过滤到账号允许的设备
        |
按信号和业务规则排序
        |
连接设备并执行完整流程
```

测试中相邻设备可能同时出现，且信号差距不稳定。因此自动模式必须保留日志，至少记录：

- 扫描启动和结束时间。
- 首次发现每个候选设备的时间。
- RSSI 样本或“不可用”。
- 设备授权是否唯一。
- 连接、通知、挑战、响应和回执阶段。
